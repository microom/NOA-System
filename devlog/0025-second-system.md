# #25 — 二台目で、設計が試された

ここまでのNOA Systemは、ずっとSuper Famicomを中心に育ててきました。

Library、PLAY、Controller、Save、Save State、AutoSnap、Preview、Overlay。

機能を追加するたびに、できるだけ「SFC専用の仕組み」にはしないようにしてきました。

でも、それが本当に共通設計なのかは、SFCしか動かしていない間は分かりません。

名前だけGeneralにしていて、実際にはSFCの事情が染み込んでいるかもしれない。

そこで、二台目のSystemとしてMega Driveを追加しました。

選んだ理由は、少し現実的でもあります。

最初のSystemにSFCを選んだのは単純に好きだったからですが、進めてみると特殊chipやcartridgeごとの差が想像以上に多く、「初手としてはかなり大変なものを選んだな」と後から気付きました。

だから二台目は、もう少し素直そうなMega Driveにしました。

そして実際に始めてみると、びっくりするほど早く動きました。

今回の話は、Mega Driveが増えたことだけではありません。

**それまで縦に積み上げてきたNOA Systemが、初めて横へ広がった話**です。

---

## 「Mega Drive版」を作らない

最初に決めたことは単純でした。

Mega Driveを追加するからといって、Mega Drive専用のGame DetailやSessionを作らない。

```text
SFC Session
MD Session
```

という二本立てにはしません。

ゲームがどのSystemなのかを見て、対応するCoreを選ぶ。

その先は、これまで使ってきた同じEmulation Sessionへ流します。

```text
Game
  ↓
System
  ↓
対応するCoreを解決
  ↓
共通のSession
```

SFC向けに固定されていた箇所は、必要な範囲だけSystemから解決できる形へ直しました。

入力まわりも同じです。

もともとlibretroの共通Controller abstractionを使っていたので、SFC用の名前になっていた部分をGeneralな名前へ整理し、Mega Drive専用Input Layerは増やしませんでした。

この段階では、まだ「設計が共通だった」とは言えません。

ただ、少なくとも二台目を無理やり横へコピーせず、同じ入口へ入れられる形にはなりました。

---

## 本当に、横へ広がった

実際のMega Drive ROMをLibraryへ入れ、Game DetailからPLAYします。

そこで二台目のCoreが選ばれ、実ゲームが起動しました。

Video、Audio、Controller、Keyboard fallback、Exit。

一通り確認して、正常にGame Detailへ戻ります。

AutoSnapを作ればPreviewも出る。

好きな**ボナンザブラザーズ**も、そこに普通にいました。

SFCの機能を作っていたときも、一つ一つ完成するたびに嬉しさはありました。

でも今回は少し種類が違います。

昨日までSFCしかいなかったLibraryで、L/Rを押すと別のSystemへ移り、そこで別のゲーム機のゲームが同じNOA Systemの中で動いている。

それまでずっと「深くする」方向へ伸びていたものが、初めて「広くなる」方向へ伸びました。

二台目が一台増えただけなのに、急にこの先の景色が見えた感じがありました。

---

## 「対応する」つもりだったSaveは、もう動いていた

さらに面白かったのは、Battery Saveでした。

Mega Drive用Save persistenceを既存Save基盤へ接続する予定だったのですが、最初にコードを追ってみると、接続するための大きな実装がほとんどありませんでした。

以前SFCのSaveを作ったときから、保存先はSystemのidentityを受け取り、Session側も特定Systemを前提にしない形になっていたからです。

Mega Driveが正式にSystemとして解決できるようになった時点で、そのまま同じ経路へ流れていました。

```text
SFC ─┐
     ├─> 共通Save基盤
MD  ─┘
```

最初の実機確認でもSave fileは生成されました。

「これは本当に、追加実装なしでいけるのでは？」

そう見えました。

でも、ここで終わらなかったのが実機確認の良いところでした。

---

## Fileは戻っている。でもゲームには戻っていない

アプリを完全に再起動して、Sonic the Hedgehog 3やShining Force IIのSaveを戻してみると、妙なことが起きました。

Save fileは読めています。

Coreへ書き戻したというLogも出ています。

終了すると、その内容はまた同じSave fileとして保存されます。

なのに、ゲーム側ではSaveが見えない。

つまり、

```text
File → NOA System → Core
```

までは一見うまく動いているのに、

```text
Core → Game
```

のどこかで意味が失われていました。

最初は、Coreが公開するSave RAM sizeが起動直後に安定していないように見えました。

そこで一度、数Frame待ちながらsizeが落ち着くまでretryする対策も入りました。

でも、それでもゲーム側にはSaveが戻りません。

ここで「このCoreはちょっと特殊だから」で済ませず、Genesis Plus GXと一般的なFrontend側のSave RAM処理まで調べ直しました。

すると、見えていた挙動は不安定なのではなく、**意図された仕様**でした。

Genesis Plus GXは、最初のgame frameを動かす前には、FrontendがSaveを読み込むための最大bufferとして64 KiBを公開します。

一方、gameplayが始まった後は、実際に使われている範囲に応じたもっと小さなsizeを返します。

つまり、604 byteのSaveを64 KiBのbufferへ読み込むこと自体が正しい。

以前のNOA Systemは安全側に倒すため、Save fileのsizeとCoreの公開sizeが完全一致しないと復元を拒否していました。

SFCではそれで問題なかった安全策が、二台目では逆に正しいrestoreを妨げていたのです。

---

## workaroundを捨てて、契約を直す

原因が分かれば、retryは不要でした。

正しい契約は、

```text
Save file <= Coreが公開するbuffer
    → その分だけrestoreしてよい

Save file > Coreが公開するbuffer
    → 安全側に失敗する
```

です。

そこでSave RAMの「完全一致で置き換える処理」と、「FrontendとしてSaveを復元する処理」を分けました。

Saveは最初のgame frameが動く**前**にbufferへ戻します。

Sonic 3とShining Force IIで再確認すると、今度はアプリを終了して起動し直しても、ゲーム内のSaveがちゃんと戻りました。

二台目は「共通設計がそのまま使えた」ことを証明してくれました。

同時に、**一台目だけでは見えなかった共通層の契約ミス**も見つけてくれました。

これもまた、Second Systemを入れる意味だったと思います。

---

## Save Stateも、AutoSnapも、Previewも

そして、その次の検証ではまた様子が変わります。

Mega DriveでManual Save State、Load State、AutoSnap、Auto Resume、Preview Screenshot、プレイ中Overlayを確認しました。

ここでは、production code側の追加修正がほとんど必要ありませんでした。

Stateにはもともと、

```text
ROM / Media identity
System
Core
Core Version
Schema Version
```

などの互換性情報が入っています。

だからMega DriveのStateをSFCへ誤って適用することもありません。

AutoSnapも同じSave State基盤の上にあります。

PreviewもFrameの幅や高さを毎回見て扱うので、System固有の固定解像度を前提にしていませんでした。

Overlayもゲーム内容には依存しません。

実際に見つかったSFC固定は、主にTest helper側でした。

本体よりTestの方が先に「二台目が来るとは思っていなかった」のは少し面白い結果です。

---

## 二台目は、新機能であり、設計の試験でもあった

SFCだけを作っている間も、ずっと「あとで別のSystemが増える」ことは意識していました。

でも設計というものは、未来を想像してGeneralにしたつもりでも、本当にGeneralかどうかは分かりません。

抽象化しすぎているかもしれない。

逆に、どこかに一台目の都合が残っているかもしれない。

二台目を実際に入れて初めて、その答えが出ます。

今回Mega Driveを追加して分かったのは、全部が完璧だったということではありません。

ROM Databaseなど、まだSystemごとに整理した方がよい部分もあります。

Save RAMのように、二台目で初めて前提の違いが見つかった部分もありました。

Cartridge Adapter側も、この時点ではまだSFC中心です。

それでも、ゲームを起動して遊び、保存し、Stateを作り、続きを残し、Previewを見て、Overlayを使って終了するという**NOA Systemの中心部分**は、同じ形のまま二台目へ広がりました。

これはかなり大きな確認でした。

---

## AIに任せれば、勝手に良いものが出てくるわけではない

今回の一連の作業には、もう一つ別の実感もありました。

Mega Drive対応が驚くほど綺麗に広がったのは、AIへ「MD対応して」と投げたからではありません。

これまで一つずつ、

- System固有にしない
- 分からないものを推測しない
- 安全側に失敗する
- 実装と設計資料を一緒に育てる
- 実機で確認する

という判断を繰り返してきました。

そして少し変な結果が出れば、そこで止めて点検する。

Save RAMのときも、最初の修正が正しそうに見えても、実ゲームで直っていなければもう一度調べ直しました。

私が資料や実装を調べ、そこで得た情報を整理し、Claudeが実装へ落とし、また人間が実機で確かめる。

どれか一つに丸投げするのではなく、結果がずれないように何度も軌道修正する。

今回二台目が綺麗に広がったのは、それまで積み上げてきたコードだけでなく、**そういう開発の仕方そのものが少し形になってきた結果**でもあるように思います。

---

## 「共通にした」ではなく、「共通だったと分かった」

今回の作業では、Mega Drive向けに大量の機能を追加したわけではありません。

最初にSystemとCoreをつなぐ。

すると多くの機能はそのまま動く。

一方、Save RAMでは二台目だからこそ一台目では見えなかった前提違いが見つかる。

そして直したあとには、その修正もMega Drive専用hackではなく、共通のFrontendとしてより正しい形になりました。

**二台目を追加したことで、初めて一台目の設計を評価できた。**

それまでSFCのために一つずつ作ってきたものが、別のゲーム機でも同じ意味を持ち始めました。

NOA Systemが「Super Famicomを遊ぶためのFrontend」から、少しだけ本当の意味で「System」へ変わった瞬間です。

そして何より、毎日縦へ積み上がっていたものが、初めて横へ伸びた。

その景色が見えたことが、今回いちばん嬉しかったことなのかもしれません。

次は、ファイルから動かすだけではなく、実際のMega Drive Cartridgeをどう扱うかへ進んでいきます。

---

## micから

最初にSFCを選んだのは単に僕が大好きなハードだったからなんだけど、始めてから「そういやこいつ、特殊chipめちゃくちゃ多いじゃん」と思ってちょっと後悔した。

だから二台目はもう少しシンプルそうなMDにした。

そしたら、びっくりするほど簡単に動いてしまった。

これは今までEchoと丁寧に作ってきた思想と、それをClaudeさんが綺麗に実装してくれたおかげだと思う。

毎日信じられない進捗が出ていたけど、この時は初めてNOAが横軸に広がった感じがして、すごく嬉しかった。

もちろん全部がそのまま上手くいったわけじゃなくて、Genesis Plus GXのSave周りでは思った挙動にならなくて、Echoにかなり深く調べてもらった。

そこで新しい情報を集めてもらって、Claudeさんへ渡して、最後はちゃんと根本から直った。

AI駆動の開発って、サイコロを転がしてたまたま良いものが出たら喜ぶ、というものじゃないんだと思う。

くどいくらい点検して、先回りして資料を集めて、思想を伝えて、間違えそうなら修正する。

特にチェックと資料集めはかなりEchoに頼ってるけど、僕自身のプログラマとしての経験も、こういうときにはちゃんと効いてる気がする。

そして好きなボナンザブラザーズがNOAの中で普通に動いているのを見たときは、やっぱり嬉しかった。
