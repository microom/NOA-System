# #19 — その瞬間を、丸ごと保存する

ゲーム内のセーブデータを残せるようになって、カートリッジとの間でも行き来できるようになりました。

普通に遊ぶだけなら、それで十分です。

でもエミュレーションには、もう一つ抗いがたい便利さがあります。

**今この瞬間を、そのまま保存しておきたい。**

今回はManual Save Stateの「保存する側」を作りました。

---

## SRAMとは、別の保存

SRAMが保存するのは、ゲーム自身が「セーブ」として残したデータです。

Save Stateはそれとは違います。

CPUやメモリなど、その瞬間のエミュレーション状態をCoreからserializeして、あとで同じ状態へ戻れるようにするためのデータです。

NOA Systemでは、この二つを同じものとして扱わないようにしました。

```text
ゲーム内セーブ
  → SRAM / Battery Save

その瞬間の状態
  → Manual Save State
```

保存先も処理も別です。

Save Stateを作ったことで、既存のSRAMが置き換わったり壊れたりしないようにしています。

---

## Coreの機能を、そのままNOA Systemの機能にしない

Stateの取得にはlibretroのserialize APIを使います。

実行中のCoreから必要なサイズを取得し、現在の状態をbyte列として受け取ります。

ただ、そのbyte列をそのままファイルへ置くだけでは、NOA System側から見れば「何のStateなのか」が分かりません。

そこでState本体と一緒にmetadataも保存します。

```text
Library/States/<Game>/
    manual_0000.state
    manual_0000.json
```

metadataには、対象Mediaのidentity、System、Core情報、State形式のversion、作成日時、slot、Stateのbyte sizeなどを持たせています。

単なるROM filenameではなくLibrary上のGame identityに結び付けることで、後から保存場所やROM名が変わっても「どのゲームのStateか」を追えるようにしました。

---

## 保存途中で失敗しても、前のStateを壊さない

Save Stateは数百KiB程度のまとまったデータになります。

書き込み途中でアプリが止まったり、metadataだけ書けたりすると、壊れたStateが正常なものに見えてしまいます。

そこで既存のSaveと同じように、一度temporary fileへ書いてからrenameで確定します。

さらに、State本体を先に確定し、そのあとmetadataを確定します。

```text
serialize
  ↓
Stateを一時ファイルへ保存
  ↓
Stateを確定
  ↓
Metadataを一時ファイルへ保存
  ↓
Metadataを確定
```

metadataが存在するなら、対応するState本体は少なくとも書き込みを終えている。

そう判断できる順番です。

途中で失敗した場合も、それまで正常だったStateは変更しません。

---

## 最初は、F5だけ

この段階ではState ManagerのようなUIはまだ作っていません。

プレイ中に`F5`を押すと、slot 0へManual Save Stateを保存します。

複数slotを扱えるよう内部のAPIは最初からslot番号を持っていますが、今は一つだけ。

まず「安全に保存できる」という土台を先に作りました。

実際のSFCゲーム2本でも、Coreを起動してserializeし、Stateを永続化してbyte単位で読み戻せるところまで確認しています。

---

## で、これどうやって確認するの？

ここまで実装すると、Stateファイルはちゃんと作られます。

テストでもserializeされたデータが保存されていることは確認できます。

レビューとしても問題ありません。

ただ、人間として確認しようとすると一つ困ります。

**まだロードする仕組みがありません。**

Save Stateという名前なのに、今できるのはSaveだけ。

「保存 → ゲームを進める → Load → 保存した瞬間へ戻る」という、いちばん分かりやすい確認は次の段階までお預けです。

こういう途中の状態も、完成した機能だけを並べるより開発記録としては面白い気がします。

ちゃんと保存できた。

でも、まだ戻れない。

次はそこをつなぎます。
