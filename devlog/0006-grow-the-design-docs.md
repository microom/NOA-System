# #6 — 作りながら、設計書も育てる

前回までで、実ゲームの起動、Save、ROM DatabaseのSource保存と再生成まで、一気に土台が具体化してきました。

実装が進むのは嬉しい。

でも、コードが前へ進むほど、最初に書いた設計文書との間には少しずつズレが生まれます。

そこで今回は次の機能へ進む前に、いったん立ち止まって設計文書を現在地へ揃えることにしました。

コードはほとんど触っていません。

それでも、NOA Systemをこの先作っていくうえではかなり大事な回だったと思います。

---

## 実装が進むと、設計書は古くなる

最初の段階では、まだ決まっていないことを決まっているように書かないよう気をつけていました。

ところが実際にゲームを起動し、Saveを扱い、ROM Databaseを作り始めると、当初は仮だった言葉の意味がだんだん具体的になってきます。

その結果、設計文書の中にいくつか「今の実装を読むと少し違って見える」表現が残っていました。

例えば、あるGameを識別するためのhashを単純に「Game Hash」と書いてしまうと、Gameそのものと、実際のROM / Mediaが同じIdentityを持つようにも読めます。

でも、同じゲームにもrevision違いやregion違いがあり得る。

今後それらをきちんと扱うなら、GameとROM / Mediaは最初から同じものとして固定しない方がいい。

そこで、この段階ではより正確な `ROM / Media Hash` という表現へ揃え、正式なIdentity設計は後で実データを見ながら決めることにしました。

---

## 「Windowsは低優先度」と「Windowsで開発する」は両立する

もうひとつ、文章だけ読むと矛盾して見える部分がありました。

NOA Systemの最終的な姿として、Windows版やSteamでの製品展開は今のところ優先度が高くありません。

一方で、現在の開発環境としてはWindows Desktopをかなり積極的に使っています。

これは別の話です。

```text
製品としてのWindows展開
    → 今は低優先度

開発・自動検証のためのWindows Desktop
    → 現在の第一開発環境
```

Windows上で先に中核部分を作ることで、特定の実機やOSに依存する処理と、NOA Systemそのものの処理を分けやすくなります。

設計としては最初からそう考えていたのですが、文章の書き方が追いついていませんでした。

今回はその違いも明示しました。

---

## 現在使っているCoreも、永久固定ではない

SFCの開発用Coreについても、初期の設計文書には単に `bsnes` とだけ書かれていた場所が残っていました。

実装ではすでに `bsnes_mercury_balanced` を使っています。

なので現在地としてはそれを正しく書く。

ただし、だからといって「NOA SystemのSFC Coreは今後ずっとこれ」とはしません。

将来、実機上の性能や互換性を確認した結果、別のprofileや別Coreの方が適切なら差し替えられる余地は残します。

**今決まっていることを正確に書くことと、未来まで固定してしまうことは別です。**

この線引きも、設計文書を整理する中で改めて意識することになりました。

---

## 今回は、コードを書かなかった

今回変更したのは設計文書だけです。

runtime behaviorもDatabase schemaも変えていません。

念のため既存の自動テストも通し、コード側に影響がないことを確認しました。

機能だけを数えれば、NOA Systemは何も増えていません。

でも、開発を続けるための「共通認識」はかなり整いました。

人間同士でもそうですが、AIと一緒に開発していると、曖昧な文章はそのまま曖昧な実装候補になります。

逆に、なぜそうしたいのか、何がまだ決まっていないのか、どこまでが現在の事実なのかを文章に残しておけば、次の作業でもそこから同じ方向を向けます。

NOA Systemでは、設計文書は実装前に完成させて終わるものではなくなってきました。

**作りながら、設計書も一緒に育てていく。**

この回で、その開発の仕方が少しはっきりした気がします。
